# vault-parser-review-pitfalls

> Class-level checklist of recurring bugs in L'Usine / Warren vault parsers (SQL IKKO, GSheet, payroll, LTO). Apply during `code-review-and-quality` or `simplify-code` on any parser/orchestrator.

## 1. Double-transformation bug (CRITICAL)
A conversion factor (`*0.882` NET_FACTOR, `/1e6` VND→M, `*pct`) applied at ONE pipeline layer AND AGAIN at another silently corrupts aggregates.
- Real case (2026-07-26, `lto_sql_parser.py`): `query_baseline_weeks` did `gross_rev * NET_FACTOR / 1e6`; `compute_baseline` then `* NET_FACTOR` AGAIN → baseline net 0.882× too small → Δ% net wrong (+2.5% reported, true −9.6%).
- **Action:** trace EVERY ×/÷ conversion through the full call chain; assert each factor applied exactly once. String-presence verify gates do NOT catch this — cross-check magnitude vs independent recompute (`verify-parser-output`).

## 2. Extensibility-claim verification (HIGH)
When a refactor claims "adding X = 1 line" (registry/SSOT), DO NOT trust it. Grep ALL hardcoded refs to old entities: title strings, verify-gate string checks, branch logic (`if store == 'LU5' else 'C...'`).
- Real case: `WINDOWS` registry looked extensible, but `build_promo_block` hardcoded B/C title via `store` branch + `verify_lto_gate` hardcoded `"B. SUNSET HH" not in payload` → adding promo D needed title logic + gate edits, NOT 1 line.
- **Action:** enumerate every place the entity name appears; confirm new entity flows through all.

## 3. TDD fixture trap (CRITICAL TDD lesson)
Green unit suite ≠ production correct. Easy fixtures hide production bugs.
- Fixture fed `gross_rev=19.6` (already-M) → passed; production returned `21004576.7` VND, forgot `*1e6` → wrong by 1e6×.
- Fixture fed `net_list=[361]` (4-week sum) → passed; production returned `[w1,w2,w3,w4]`, `compute_baseline` divided by `len==4` → baseline 4× too small.
- **Action:** fixtures must mirror REAL data shape (per-week lists, raw VND). After unit GREEN, run ≥1 E2E dry vs real source + cross-check magnitude vs independent recompute.

## 4. Dead imports / no-op flags (MEDIUM)
- Unused imports (`re, json, argparse, date, timedelta` when date-math lives in caller).
- No-op CLI flags (`--no-tg` accepted but never used → misleading).
- **Action:** `grep -n "import" file.py` + check each symbol usage; grep flag against actual use.

## 5. Query-count dedup (MEDIUM, perf)
Count actual DB round-trips, not assumed. Real case: `build_payload` queried B+C covers, then FBM-read re-queried same covers → 12 queries vs 8.
- **Action:** trace every DB call in hot path; flag re-fetches of already-available data.

## 6. Discount-name blind spot (HIGH — cost-layer corruption)
The `Discounts` table stores promo under OPERATIONAL names that differ from the marketing label. A `LIKE '%Sunset%'` guess can (a) MISS the real row, or (b) match but the assumed % ≠ actual — silently corrupting the GP-incrementality cost layer by ~5×.
- Real case (2026-07-26, LTO W27): block computed disc = 15% × net = 3.1M; actual `LU5_DSC_OPS_15%_SunsetHappyHour` = 0.60M. ~5× gap. The LIKE pattern DID catch the row, but the ×pct assumption was wrong; enumerating real names exposed it.
- **Action:** BEFORE trusting any discount cost, enumerate ALL discount names per store-week (`SELECT DiscountName, SUM(Amount) ... GROUP BY DiscountName`) and pick the exact operational name. Never derive cost as pct × net_rev. The pct in the name string is the only authoritative rate.
- Generalize: any 'cost from a table' layer must be sourced FROM the table, not re-derived by formula.

## 7. Baseline-window pollution (MEDIUM)
Selecting baseline weeks by a loose predicate catches the promo weeks too, shrinking the baseline and inflating Δ%.
- Real case: `if wk.startswith('W2')` pulled W23–W26 AND W27/W28 into baseline → avg_net wrong, Δ% net off.
- **Action:** baseline weeks MUST be an explicit tuple list (`('W23','W24','W25','W26')`), never a prefix/regex over week keys that also matches promo weeks.

## 8. Reviewer-node timeout fallback (PROCESS)
When the A10 independent reviewer subagent times out (no summary returned), DO NOT skip verification. The gate's purpose is independent challenge — a timeout removes it, so the agent must self-supply at least one independent second-source check (e.g. enumerate discount names, re-run with a different query shape, re-derive baseline by hand) before writing SSOT. Also: never emit a gate token ('reviewer chạy...') before the tool call is actually dispatched — token = proof-of-work, not a promise.

## 9. Dotfolder search blindness (TOOLING — load FIRST on any parser review)
Parsers live in `10_OPERATION_DATA/.parsers/` and shared libs in `vault/.scripts/` — BOTH dotfolders. `search_files` / ripgrep skip hidden dirs by default and return `total_count: 0` SILENTLY (no error), which reads as a false "no duplication / no match found."
- Real case (2026-07-26): repo-wide `search_files` for `NET_FACTOR|_monday_of_week|make_week_id` returned 0; a passed path INTO `.parsers/` even errored `IO error ... cannot find the path`. Only `terminal` `grep` with explicit `cd` into the dotfolder worked.
- **Action:** for any search that must cover `.parsers/` or `.scripts/`, use `terminal`: `cd "<abs .parsers path>" && grep -rn "pattern" *.py`. NEVER conclude "not found / no dup" from a `search_files` zero-count when the target is a dotfolder.

## 10. Code-reuse / duplication landscape (for reuse-only reviews)
Shared helper libs EXIST but are imported by NOBODY — every parser inlines its own copy. Know this before flagging or "fixing":
- `vault/.scripts/_utils.py` — `make_week_id`, `insert_or_replace_weekly`, `prev_week_bounds`, `fmt_*`, gviz helpers. Zero importers.
- `vault/.scripts/_week_utils.py` — `current_week_bounds`, `completed_week_bounds`, `prev_week_bounds`, `make_week_id`. Zero importers.
- **SQL bootstrap** — `_setup_sql_env()`, `_run_sql()`, `NET_FACTOR=0.882`, `STORE_MAP` ("LSLTT"→"LU3"), `_sqlclient` global — near-identical across `revenue_sql_parser.py`, `lto_sql_parser.py`, `hourly_cover_sql_parser.py`. ⚠️ NOT byte-identical anymore (2026-07-26 altitude review): the hourly copy alone adds `os.environ["MSSQL_DATABASE"] = "iikoAPI"` (`hourly_cover_sql_parser.py:64`) — a per-caller special-case snuck into a copied infra function via process-global env mutation. Proof the copies drift; deeper fix is a `get_sqlclient(database=None)` param, not another env poke.
- **NET_FACTOR is 4 copies, not 3** — also `.scripts/monthly_aggregation.py:31`. When counting duplication, grep `.scripts/` too, not just `.parsers/`.
- **TWO parallel utils TREES, not just two files** — `vault/.scripts/{_utils,_week_utils}.py` AND `vault/10_OPERATION_DATA/.scripts/modules/{_utils,_frontmatter,_week_utils,cph_config}.py`. The `_week_utils.py` copies were byte-identical on 2026-07-27 (`diff` → IDENTICAL) but nothing syncs them. The "which one do I import?" ambiguity is WHY new helpers (e.g. grabfood cron guard) re-implement instead of importing. Note: `modules/` IS live — SKILL.md crons set `PYTHONPATH=vault/10_OPERATION_DATA/.scripts/modules`, and grabfood_parser imports `_utils` from there. Consolidation = own task, CAREFUL (PYTHONPATH assumptions in several crons).
- **Shared week infra is ITSELF duplicated** — `make_week_id` lives in BOTH `.scripts/_utils.py:90` AND `.scripts/_week_utils.py:42`; `_monday_of_week`/`_sunday_of_week` have a 3rd verbatim copy in `.scripts/weekly_lto_sql.py:42-52` (the LTO orchestrator). Any consolidation must also collapse the two `_utils` variants into one.
- **Dashboard-refresh band-aid duplicated + broken copy** — the `importlib.util.spec_from_file_location("gen_hourly_dashboard", ...)` + `node --check` block exists in `hourly_cover_parser.py:724` AND `hourly_cover_sql_parser.py:508-538`. The SQL copy calls `shutil.which("node")` WITHOUT importing `shutil`; the NameError is swallowed by a blanket `except Exception` → the JS check silently never runs ("JS check skipped" every time). Lesson: a copied safety gate wrapped in broad try/except can be dead for months with zero signal — verify every name inside a try-block is actually imported. Deeper fix: one shared `refresh_dashboard(gen_script, html_path)` util in `.scripts/`.
- **Week-date math** — `_monday_of_week` / `_sunday_of_week` duplicated across `revenue_sql_parser.py`, `revenue_screenshot_parser.py`, `hourly_cover_sql_parser.py` (4+ copies with `make_week_id`).
- `STORE_MAP` has already DRIFTED: SQL parsers use `{"LSLTT":...}` (DB dept codes) while GSheet `hourly_cover_parser.py` uses `{"LU3-LTT-Q1":...}` — proof drift is real, not hypothetical.
- **Worked case — `item_sales_sql_parser.py` (2026-07-27 REVIEWER-1):** byte-exact `iso_week(d)` (L47-49, `return f"{y}-W{w:02d}"`) duplicates `_utils.make_week_id()` (`_utils.py:90`) — highest-leverage, lowest-risk flag (^F1). The SQL bootstrap (`_run_sql`/`_setup_sql_env`, sqlclient env wiring) is a verbatim copy again (L16-26 = `revenue_sql_parser.py:43-58`) — extract one `run_sql()` into `_sql_common.py` (^F4). `gen_item_sales_dashboard.py` is a DEAD generator feeding the SAME `item_sales_trend.html` but an INCOMPATIBLE JSON schema (`__PAYLOAD__` + `{weeks,current.System,...}` vs the live `__PAYLOADS__` + `{week,system,stores,bcg,...}`) — confirm live pipeline before archiving (^F8). Full evidence: `references/2026-07-27-reviewer1-item_sales-reuse.md`.
- **Chesterton caveat:** "just import the shared util" does NOT match any live runtime path (nobody imports them). Recommend consolidation as the fix but flag it as CAREFUL/new-dependency, not a like-for-like swap. Precedent that IS live: `revenue_sql_parser.py` does `from revenue_screenshot_parser import build_payload, verify_gate, ...` — cross-parser import is accepted in this repo.
- **Non-dups to skip:** `write_log_atomic` (richer than `_utils.insert_or_replace_weekly` — preserves frontmatter + template + atomic os.replace); independent SSOT re-parse (`parse_ssot_week` deliberately independent, 2% vs old 5% threshold); same-named `verify_gate` across files that check DIFFERENT invariants. Confirm by reading BOTH sides before calling anything a dup.
- **SSOT re-parse nuance (altitude):** independence of the cross-check parse is intentional (A9) — do NOT propose sharing parsed VALUES. But the table-format GRAMMAR (section-header regex `## YYYY-Wxx | start → end`, `### Full Week`, row labels `Net Revenue`/`Covers`) is duplicated between `revenue_screenshot_parser.build_block` (writer) and `hourly_cover_sql_parser.parse_ssot_week:370` (reader); a format change breaks the reader silently → false "DATA GAP". Correct deeper fix: share format-spec CONSTANTS only, keep parse call sites independent.

## 19. Week-ID year-convention mismatch (HIGH — year-boundary desync between writer and reader)
Multiple inline week-id formulas coexist and DISAGREE on which year to use. Any pair of scripts where one WRITES `## <week_id>` headers and another SEARCHES for them (guard, dedup, prev-week lookup) silently desyncs on the year-boundary week:\n- `f\"{ws.year}-W{iso:02d}\"` — Monday's CALENDAR year (`grabfood_parser.py:386,396,626`; also `_utils.make_week_id` / `_week_utils.make_week_id` use `week_start.year`).\n- `last_sun.isocalendar()` → true ISO year (`ops-grabfood-cron` guard `compute_week_id`).\n- `date.today().isocalendar().year` — ISO year of TODAY, not of the target week (`run_weekly_revenue_pipeline.py:59`).\n- Real case (2026-07-27 altitude review): week Mon 2025-12-29→Sun 2026-01-04: parser writes `## 2025-W01`, guard searches `2026-W01` → never matches → guard returns RUN every tick → the 20×/Monday spam the guard exists to prevent returns exactly once a year. Zero tests catch it (all fixtures use mid-year dates).\n- **Action:** on any review touching week-ids, list EVERY formula variant (`grep -rn \"isocalendar\\|-W{\" …` via terminal, dotfolders! §9) and check writer/reader pairs use the SAME convention. Canonical fix = one shared `make_week_id` based on `isocalendar()` ISO year, imported by BOTH sides — but changing the writer's convention alters existing log headers near New Year → CAREFUL, coordinated change. Add a year-boundary date (e.g. Mon 2025-12-29) to any week-id test.\n- **Altitude verdict pattern (guards):** a cron-specific SKIP/RUN guard is the RIGHT altitude for run-policy; only its date/week math belongs in shared utils. Flag the math duplication, keep the guard.\n\n## 20. Orchestrator-vs-parser WEEK-CONVENTION mismatch (HIGH — cron guard inert + summary fallback)
When a no_agent cron WRAPPER invokes a parser to append a weekly entry, the wrapper often computes "this week" INDEPENDENTLY of the parser. If the two conventions/offset differ, the wrapper's guard + summary target a week the parser NEVER writes → guard is a no-op and the Telegram summary always hits its "not found" fallback (green-but-data-less, mislabeled). Distinct from §19 (year-boundary desync) — this is a same-year OFFSET/convention mismatch.
- Real case (2026-07-27 review of `google_review_monday_cron.py` + `google_review_parser.py`):
  - Wrapper `compute_current_week_label(d)` = `d.isocalendar()` → **Monday-ISO CURRENT week** (`2026-W31` on Mon 2026-07-27; `2026-W32` on the first real run 2026-08-03).
  - Parser `detect_week()` is **Sunday-based**; `build_entry` writes `week_start.isocalendar()` = the **PRIOR** ISO week (`2026-W30` / `2026-W31`). They NEVER match.
  - Consequence: `should_skip(log, compute_current_week_label())` checks W31/W32 (never in log) → always RUNS; `format_tg_summary(log, compute_current_week_label())` searches W31/W32 (never present) → always returns `"✅ … đã cập nhật (không tìm thấy entry để tóm tắt)"` — a green-but-data-less, MISLABELED message. The function itself is correct (passing W30 yields the proper `"🟢 … W30 / System avg★: 5.0 | R/1k: 2.0"`); it is fed the wrong week.
  - Duplicate protection then relies entirely on the parser's OWN in-body `if week_id in body` dedup — the cron guard provides ZERO protection and misleads logs (`week_id = 2026-W31` while W30 lands).
- **Action (verify parity — do NOT trust the submission's "verified facts"):**
  1. `terminal` grep the wrapper for its week formula AND the parser for ITS week formula (dotfolders! §9). List both conventions.
  2. Execute BOTH for the cron's real `next_run_at` dates (jobs.json `next_run_at`) and assert wrapper-week == parser-written-week. Concrete probe (adapt paths):
     ```python
     import sys; sys.path.insert(0, r"<vault>/.scripts")
     import google_review_monday_cron as C
     from datetime import date, timedelta
     for d in [date(2026,7,27), date(2026,8,3)]:
         cw = C.compute_current_week_label(d)
         wend = d - timedelta(days=(d.weekday()+1)%7); wstart = wend - timedelta(days=6)
         pw = "{}-W{:02d}".format(wstart.year, wstart.isocalendar()[1])
         print(d, cw, pw, cw==pw)   # must be True on EVERY run date
     ```
  3. Test the INTEGRATED flow, not the unit in isolation. A unit test that hardcodes `should_skip(text,"2026-W30")` / `format_tg_summary(text,"2026-W30")` is GREEN even though production passes `compute_current_week_label()` (W31/W32). Force tests to call `compute_current_week_label()` and feed its RESULT into guard/summary against the real log (false-green pattern — see §3).
- **Deployment-sync pitfall:** the cron JOB runs the copy in `profile/scripts/` (no_agent `script:` name resolves there), NOT necessarily the `vault/.scripts/` copy you reviewed. `diff` the two before signing off — they CAN differ (here they differed only cosmetically + the intended `ok 05`→`ok rv` edit was only in the profile copy). Review the RUNNING copy.
- Canonical fix shape: wrapper derives the target week from the SAME function the parser uses (import/clone the parser's `detect_week`/`make_week_id`), or pass `--week` through and read back the written `## <week_id>`. One shared `make_week_id` (§19) used by BOTH sides removes the drift.
- Reproduction + exact line refs: `references/2026-07-27-google-review-cron-week-mismatch.md`.

## 11. Legacy-format ghost entries after pipeline migration (HIGH)
When a tracker migrates pipelines (GSheet → SQL) and the entry header format changes (`## W23` → `## 2026-W23`), the new upsert's dedup matches ONLY the new header string — old-format blocks survive at the bottom of the file → same week appears TWICE with DIFFERENT numbers (old pipeline vs new).
- Real case (2026-07-27, `item_sales_sql_parser.py upsert_week`): backfill W18-W29 claimed "12 entries, no dup" — but `grep -n "^## W[0-9]"` found 6 legacy `## W18`..`## W23` GSheet blocks below line 748; legacy W23 = 4,828 items/571.6M vs new W23 = 5,211/663.7M. Dashboard unaffected (reads JSON blocks only), but humans/LLMs reading the tracker hit contradictory numbers for the same week.
- **Action:** on any "no dup" claim after a migration/backfill, grep ALL H2 variants (`grep -n "^## "` then filter out the new format), and compare total-entry count vs claimed count. Also check frontmatter: `data_source`/`parser`/`refresh_cadence`/`last_updated` often still declare the OLD pipeline (same file `:10-16,34` still said GSheet + parser v2.0).

## 12. Template self-overwrite — build output consumed the placeholder (MEDIUM)
Build flow: `template.html` contains `__PAYLOADS__` → parser emits `<stem>_build.html` → someone renames the built file ONTO the template path. The placeholder is gone; the next `--emit-html` run replace-noops and emits OLD data **silently stale** (no error), while spec commands still point at the now-built file.
- Real case (2026-07-27): `item_sales_trend.html` was the BUILT output (0 `__PAYLOADS__` hits); the real template survived only in `_archives/dashboards/item_sales_trend_template_*.html`; the `_build.html` intermediate claimed in the handoff did not exist on disk.
- **Action:** before trusting re-runnability, `grep -c "__PAYLOAD" <emit-html target>` must be ≥1; template and built output must live at DISTINCT paths. Cross-check dashboard vs tracker with an independent totals recompute: sum qty/rev_vnd over tracker JSON blocks and over the HTML PAYLOADS array — must match exactly (here 65,750 items / 8,452.5M both sides, 12 weeks each).

## 18. Tracker-block upsert migration — shared helper pitfalls (HIGH, 2026-07-27 PART2)
Extracting a duplicated "newest-on-top week-block upsert" into one helper (`_tracker_writer.py`) and migrating ≥3 parsers onto it surfaced these recurring traps. Apply on ANY such consolidation.
- **Byte-identical vs OLD is a RABBIT HOLE.** OLD `write_log_atomic` (hourly) inserts a redundant `---` + extra blank between blocks; chasing byte-equality wastes cycles. Switch the migration test to **structural equivalence**: same week-set + DESC order + per-block content match after normalizing `\n{3,}`→`\n\n`. The helper is CLEANER than OLD — it SHOULD differ in whitespace. (Real: 18-char chase loop on hourly spacing, resolved by going structural.)
- **Non-week `## ...` sections get DROPPED.** Helper identifies week blocks by `^\d{4}-W\d{2}$` header; anything else (`## Monthly Summary — July 2026`) is skipped UNLESS you capture it into `other_blocks` and re-emit AFTER week blocks. Forgetting this silently deletes monthly summaries from the tracker. (Reviewer caught this as NEEDS-FIX.)
- **Dead variable after migrate.** When the old function did the upsert inline, a computed section (`monthly_block` in `col_weekly_parser`) was written as part of the same string. After switching to `upsert_week(content, wk, entry)` (week-only), that variable is computed but NEVER written. Must wire it manually into the write path (append to `body_out` before `write_frontmatter`). Grep every computed var for a write-site before claiming done.
- **Dotfolder import path math.** Helper at `vault/.scripts/`; parsers at `vault/10_OPERATION_DATA/.parsers/`. Correct import path from a parser = `Path(__file__).parent.parent.parent / ".scripts"` (3 ups: `.parsers`→`10_OPERATION_DATA`→`vault`). Off-by-one = `ModuleNotFoundError`. (`search_files` can't see dotfolders — use `terminal` `grep`/`cd`, see §9.)
- **Double-wrap `sys.stdout` in test harness.** Parsers do `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, ...)` at import; a test that imports the parser AND `print()`s dies with `ValueError: I/O operation on closed file` (the wrapper closes the shared buffer on GC). Fix: write test results to a `_result.txt` via a fresh `open()` fd, or capture `sys.__stdout__` before importing the parser. Same root as §14.
- **reviewer-node gate is MANDATORY and two-pass.** Bố rule (2026-07-27): spawn `reviewer-node` (delegate_task, leaf) after migrate; if NEEDS-FIX, FIX then RE-RUN the reviewer (second delegation) before declaring safe. Do NOT commit until the second review returns SAFE, and Bố must approve the commit itself (Commit-Push Self-Gate).
- **Don't delete a local function's file-not-exists branch blindly.** `write_log_atomic` had a `if not log_file.exists(): create minimal frontmatter` branch. The helper's `write_tracker_block` already covers create-if-missing — migrate to that, don't just delete and lose the create path.
- **Test-file staleness after removing a local fn.** When you delete a parser's local writer (`write_log_atomic`), its unit tests (`run_hourly_sql_tests.py`) still call `H.write_log_atomic(...)` → `AttributeError` at runtime (production unaffected). Grep the test file for the removed name and point it at the helper (`write_tracker_block(f, wk, block, prefix_mode='template')`). Fix before declaring done (reviewer flagged as non-blocking cleanup).
- **Trackers with NON-week `## ...` headers need the separator regex to ALSO match.** `07_COL_Weekly_Log.md` has `## Monthly Summary — July 2026` (space, not `YYYY-Wxx`). Any `re.split(r'^(## 2026-W\d+.*)$')` approach (old `sort_week_blocks_on_top`) DROPS the summary into "others" and can drop it on reassemble. The helper keys week-blocks on `^\d{4}-W\d{2}$` and captures everything else into `other_blocks` re-emitted after weeks — verify the summary survives an upsert (reviewer test: inject `## Monthly Summary — Test 2026`, assert still present after `upsert_week`).
- Helper + consumers live in: `vault/.scripts/_tracker_writer.py`; consumers `item_sales_sql_parser.py`, `hourly_cover_sql_parser.py`, `col_weekly_parser.py` (all migrated PART2). Skill governing the helper: `tracker-writer` (user-owned — `hermes curator adopt` to edit).
- Obsidian-native dashboard (Mermaid, zero-plugin) technique + `emit_item_sales_mermaid.py` gotchas: `references/obsidian-native-dashboard.md`.
- **HTML dashboard renders BLANK in Obsidian (blocked `<script>`); browser-only.** `item_sales_trend.html` (Chart.js embedded inline, data valid) shows charts ONLY in Chrome/Edge, NOT in Obsidian preview (Obsidian strips `<script>`). If Bố reports "trắng", confirm the open surface: Obsidian tab = expected-blank; copy the `file:///` link into a real browser, or use the Mermaid Obsidian-native note (`Item_Sales_Dashboard.md`) which renders inside Obsidian with zero plugins. Don't chase a "data bug" in a valid HTML — the data is fine, the surface blocks JS. (Browser tool also BLOCKS `file://` URLs as private — can't headless-render to diagnose; rely on JSON.parse-validity + Bố's open-surface confirmation.)

## 13. Dangling reference after dedupe / inline (HIGH — silent runtime crash)
When you collapse a repeated computation (e.g. `agg_prev = aggregate(rows_prev)` computed twice in one function; keep one, delete the other), the SECOND reference to the old name survives the edit and raises `NameError` only at **runtime**, not at import. The module imports fine, isolated unit tests that don't hit that branch pass, and the failure appears only when the real path runs.
- Real case (2026-07-27, `item_sales_sql_parser.build_payload`): deduped `prev_agg`→`agg_prev`, but the per-store delta lines `dq = ... if (prev_agg and ...)` still referenced `prev_agg` → `NameError: name 'prev_agg' is not defined` at W29 build time.
- **Action:** after any function-internal dedupe/rename, `grep -n` the WHOLE file for the removed identifier; update or delete every reference. Then re-run the ACTUAL code path (not just import + isolated unit) before claiming done. A mid-function `NameError` is invisible to import-time checks.

## 14. ab-test = proof a simplify preserved behavior (HIGH — do before/after every simplify)
A simplify (even "SAFE" dead-code removal) must be proven behavior-preserving, not assumed.
- Pattern that worked (2026-07-27): import the baseline module → call `build_payload()` → deep-compare the result against a temp copy of the simplified module's `build_payload()` (ignore float `rev_vnd` noise). Equal → behavior preserved. This catches BOTH dangling references (§13) AND silent value drift in one shot.
- Also use it when the user asks for `ab-test` in the quality pipeline: baseline = current module, after = simplified module, compare payload/diff for equality.
- **Caveat:** if the module under test rebinds `sys.stdout` at import (common in vault parsers: `sys.stdout = io.TextIOWrapper(...)`), an ab-test script that `import`s it and then `print()`s results dies with `ValueError: I/O operation on closed file`. Write results via `sys.stderr.write(...)`, or import a temp copy of the module. This is the same root cause as the verify-parser-output stdout-rebind pitfall.

## 15. `simplify-code` parallel fan-out is capped at 3, not 4 (PROCESS)
The `simplify-code` skill text says "launch four reviewers in parallel" but `delegation.max_concurrent_children` is **3** on this profile → a 4-task batch is REJECTED at dispatch (`Too many tasks: 4 provided, but max_concurrent_children is 3`).
- **Action:** split into two batches — batch 1 = Reviewers 1+2+3 (Reuse/Quality/Efficiency), batch 2 = Reviewer 4 (Altitude) after. Or fold Altitude into one of the first three if the change is small. Never dispatch 4 in one `delegate_task` call here.
- Also: when `git diff` / `git diff HEAD` come back near-empty because the target file was edited earlier THIS session and never committed (untracked or pre-session baseline), do NOT conclude "nothing to simplify" — pass the **full current file content** as the diff source to reviewers (they can still search the wider codebase for reuse/context). Real session: a 397-line parser simplify showed only 6 diff lines because the pre-simplify version was never committed.

## 16. Parser→dashboard literal duplication (HIGH — cross-boundary drift)
When a parser emits an HTML dashboard (e.g. `item_sales_sql_parser.py --emit-html` injects `__PAYLOADS__` into a template), the generated HTML often RE-DECLARES config constants the parser already owns, instead of reading them from the injected payload. Two sources of truth → silent drift.
- Real case (2026-07-27, `item_sales`): dashboard HTML hardcoded `const stores=['LU3','LU5','LU7']` (L121) AND `p.week.replace('2026-','')` (L188), while the parser owns `STORES=["LU3","LU5","LU7"]` (L30) and the year sits in each payload's `week` string. Adding a 4th store (or spanning a year boundary) silently breaks the dashboard: `stores.map(s=>P.stores[s][field])` throws on a missing key, or the label shows a wrong year, while the tracker/JSON stay correct. Same pattern: `renderTrend` L188 `'2026-'` is year-coupled — would mislabel W-strings from a different year.
- Also flagged in the same review: copy-paste-with-variation inside the HTML (`revBar` vs `qtyBar` `new Chart` calls, L150-155) and inside the parser (`top_food` vs `top_bev` comprehensions L169-170; `food_union` vs `bev_union` build loops L228-246) — DRY via a `union(key)` / `barChart(id,field,label,color)` helper.
- **Dead dashboard generator with incompatible schema (REVIEWER-1, 2026-07-27):** `gen_item_sales_dashboard.py` is a SECOND generator for the same `item_sales_trend.html` but injects `__PAYLOAD__` expecting a DIFFERENT shape (`{weeks,current.System,qty_series,...}`, L32-93) than the live SQL-parser `--emit-html` path which injects `__PAYLOADS__` with `{week,system,stores,bcg,scatter,cost_missing}`. Two generators + two JSON schemas + one HTML file = a latent break. The live path (SQL parser `--emit-html`, template in `_archives/dashboards/item_sales_trend_template_*.html`) is the one that actually produces the committed built file. Action: confirm which pipeline is wired before archiving the other; never leave two emit paths for one dashboard.
- Action (during any parser→dashboard review): grep the dashboard HTML for literals that also live in the parser (store codes, year, category lists, color maps, `1e6` VND→M). The HTML must DERIVE these from `PAYLOADS`/`P` (`const stores = Object.keys(P.stores)`, `p.week.split('-')[1]` for the `Wxx` label), never re-declare them. Flag any hardcoded literal that duplicates a parser constant as a drift risk. Principle: the parser is SSOT for config; the dashboard is a VIEW and must consume injected data. (This is the parser→HTML face of the shared-state duplication problem in #10.)

## 17. Efficiency review shapes for weekly SQL parsers (MEDIUM-HIGH — extends #5)
Found via efficiency review of `item_sales_sql_parser.py` (2026-07-27); these shapes recur across all weekly IKKO SQL parsers (each fetches this-week + prev-week for W/W delta):
- **Backfill double-fetch (2N queries instead of N+1):** each per-week invocation fetches `rows_this` + `rows_prev`; a bash loop over N weeks (the spec's documented backfill pattern) re-fetches every week twice over VPN. Fix: `--backfill Wa..Wb` mode in ONE process carrying `rows_prev = rows_this` between iterations. Bonus: also nearly halves pyodbc connect/login handshakes — `sqlclient.run_query` opens a fresh connection per call.
- **Full re-aggregate for 2 scalars:** `main()` calls `build_payload(prev, None, rows_prev, None)` a second time just to get `prev_payload['system']['qty','rev']` for the markdown W/W line, when the first `build_payload` already computed `agg_prev` internally. Fix: return `prev_system: {qty, rev}` from the first call. (Careful with §13 when deduping.)
- **`if False else <expensive-expr>` dead loop:** `for i,d in enumerate(<expr> if False else <O(n²) sorted/set/nested-sum expr>, 1): pass` — the taken branch STILL evaluates fully, then is discarded; leftover from an abandoned approach with the real code below it. Also grep for computed-then-unused vars (`prev_sys_qty`/`prev_sys_net` appeared only at their own definition — grep-confirm before flagging).
- **Row-grain fetch, client-side SUM:** SELECT pulls per-bill-item rows over VPN then Python aggregates. Push `GROUP BY dept, group, name` with `SUM(qty), SUM(gross), SUM(cost*qty), SUM(CASE WHEN cost>0 THEN qty ELSE 0 END)` server-side → rows drop from thousands to ~menu size. CAREFUL: verify one week identical before switching (NET_FACTOR × SUM commutes so values should match).
- **Read-before-write flag ordering:** `--emit-html` reads the tracker at L363 but `--live` writes it at L390 — combining both flags in one run builds the dashboard WITHOUT this week's entry (silent stale, no error). Fix: emit-html AFTER live-write, reusing the in-memory updated content. Generalize: whenever one CLI flag reads a file another flag writes, enforce write→read order.
- **Silent `except Exception: pass` on tracker JSON-block parse:** one corrupt HERMES JSON block silently drops that week from the multi-week trend. Fix: warn to stderr with `_m.start()` offset + print `({len(arr)}/{expected} weeks)` so a shortfall is visible.
- **Non-atomic tracker write + TOCTOU:** `exists()`→`read_text()`→`write_text()` on a 700+-line SSOT tracker; crash mid-write corrupts it with no backup. Fix: write `.tmp` sibling + `os.replace`; drop the exists-check, let `read_text` raise FileNotFoundError naturally.
