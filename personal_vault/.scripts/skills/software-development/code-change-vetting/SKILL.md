# Code Change Vetting — Safety Gate Before Accepting Any Refactor

> **Purpose:** The #1 failure mode of AI-generated refactors is **logic deletion disguised as cleanup**. This skill encodes the detection pattern + fix workflow.

---

## Trigger

You are about to accept/merge/run code that was produced by:
- Another AI model claiming to have "upgraded" existing code
- A subagent returning a "refactored" or "improved" version
- A PR or paste from an external source labeled "cleanup" or "modernize"

→ Load this skill BEFORE evaluating the change.

---

## Step 1 — Diff Against Original

If you have the original (pre-change) code:
```
git diff original..new | head -200
```
If the original is only in chat context (pasted), reconstruct both versions and compare manually.

**Key question:** What was REMOVED, not just what was ADDED?

---

## Step 2 — Count Functions / Logic Blocks

| Check | Command / Method |
|-------|-----------------|
| Function count before vs after | `grep -c "^def " original.py` vs `grep -c "^def " new.py` |
| Business logic lines | Count lines in gen_* / compute_* / parse_* functions |
| Boilerplate lines | Count logging, argparse, validation, path-check functions |

**Red flag:** Functions dropped >20%, OR business-logic lines dropped >20% while boilerplate increased.

---

## Step 3 — Search for Placeholders

```bash
grep -n "\.\.\." new.py          # literal "..." — often means "fill this in"
grep -n "similar to" new.py      # "Implementation similar to v1" = NOT IMPLEMENTED
grep -n "should copy" new.py     # "You should copy..." = placeholder
grep -n "placeholder" new.py     # explicit admission
grep -n "Content generated" new.py  # stub output text
```

Any hit → the "upgrade" is incomplete. Reject.

---

## Step 4 — Verify Call Chains

For every refactored function in the new version:
1. Is it actually CALLED anywhere? `grep -n "function_name(" new.py`
2. If the original called it N times and the new version calls it 0 times → broken call chain.

---

## Step 5 — Dry-Run Test

```bash
python new.py --dry-run --verbose 2>&1 | head -50
```

If it crashes with `TypeError`, `NameError`, or produces literal placeholder text → reject.

---

## Decision Rule

```
IF (boilerplate_added > 40% of original) AND (business_logic_removed > 20% of original):
    → REJECT the upgrade
    → Patch the ORIGINAL with only the real improvements
ELSE IF (placeholder_found OR function_count_dropped > 5):
    → REJECT — incomplete work
ELSE IF (dry_run_crashes):
    → REJECT — untested
ELSE:
    → ACCEPT — genuine improvement
```

---

## Fix Pattern (When Upgrade Is Rejected)

Do NOT try to fix the "upgrade" — you'd be rebuilding deleted logic from scratch. Instead:

1. Start from the WORKING original
2. Extract only the genuinely new improvements (logging, --verbose flag, validation)
3. Patch them into the original one-by-one
4. Verify after each patch
5. Run full dry-run at the end

**Time saved:** 30 minutes (patching original) vs hours (rebuilding deleted logic from the broken upgrade).

---

## Session Example (2026-07-21, warren-profile)

- **Trigger:** Qwen 3.8B presented `weekly_synthesis_v2.py` as an "upgrade" of `weekly_synthesis.py`
- **What was added:** logging, argparse --verbose, validate_environment (~90 lines)
- **What was deleted:** 11 gen_* functions, newest_entry(), get_source_path() (~250 lines of business logic)
- **Output:** literal `"*(Content generated by refined gen_* functions)*\n"` instead of real synthesis
- **Verdict:** Rejected. Patched V1 directly with the 3 real improvements.
- **See:** `references/2026-07-21-weekly-synthesis-v2-failure.md` for full before/after comparison.

---

## Boundaries

| Always | Never |
|--------|-------|
| Diff against original before accepting | Trust "upgraded" label without verification |
| Count functions before/after | Accept code with placeholder comments |
| Dry-run before merging | Rebuild deleted logic — patch original instead |
| Grep for `...` / `similar to` / `should copy` | Assume AI refactors preserve all logic |
